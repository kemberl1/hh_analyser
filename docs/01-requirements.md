# 01 — Требования (Requirements)

> Нумерация: **FR-x** — функциональные требования, **NFR-x** — нефункциональные.
> Приоритеты: **MUST** (обязательно для MVP), **SHOULD** (желательно), **COULD** (опционально), **LATER** (поздние фазы 6–7).
>
> **Статус:** MVP + Phase 8 (Backfill) реализованы. Все MUST-требования, фичи фаз 6–7 и Phase 8 реализованы и проверены. Исключения и упрощения помечены явно (см. §3 и [`07-roadmap.md`](07-roadmap.md) «Известные ограничения»). Ранее помеченные `LATER (Phase 6–7)` требования теперь реализованы.

## 1. Функциональные требования (Functional Requirements)

### 1.1. Сбор данных (парсинг)

| ID | Приоритет | Требование |
|----|-----------|------------|
| FR-1 | MUST | Система собирает вакансии с hh.ru по специальности **Frontend**, регион — **вся Россия**. |
| FR-2 | MUST | **Основной (primary) путь сбора — HTML-парсинг** страниц поиска и страниц вакансий на hh.ru. На момент проектирования Phase 2 публичный `api.hh.ru` недоступен, поэтому HTML-парсинг является путём по умолчанию. |
| FR-3 | MUST | **Фолбэк (fallback) — публичный API `api.hh.ru`** (`GET /vacancies` с фильтрами + `GET /vacancies/{id}` для деталей). Включается **по флагу конфигурации / при доступности** API (на будущее — если он снова заработает). Переключение источника логируется. |
| FR-4 | MUST | Сбор **идемпотентен**: повторный парсинг той же вакансии не создаёт дубликат, а обновляет запись (upsert по `hh_vacancy_id`). |
| FR-5 | MUST | Для каждой вакансии сохраняются: `hh_vacancy_id`, название, работодатель, зарплата (от/до, валюта, gross/net), `published_at`, опыт, формат работы, ключевые навыки, грейд, ссылка на оригинал. |
| FR-6 | MUST | Грейд (Junior/Middle/Senior) определяется по полю опыта hh.ru и эвристикам по названию/описанию (см. [`04-metrics.md`](04-metrics.md) §«Определение грейда»). |
| FR-7 | MUST | Нормализация данных: валюты, единый справочник навыков (skill canonicalization), формат работы, опыт. |
| FR-8 | SHOULD | Система фиксирует «сырой» ответ источника для возможности переобработки без повторного парсинга: для HTML-источника — `raw_html`/`raw_payload`, для API-фолбэка — JSON; сохраняется также `source_type` (`html` / `api`). |
| FR-9 | MUST | Сбор устойчив к частичным сбоям: ошибка по одной вакансии не прерывает весь прогон; ведётся учёт успешных/неуспешных. |

### 1.2. Планировщик (scheduler / CRON)

| ID | Приоритет | Требование |
|----|-----------|------------|
| FR-10 | MUST | Ежедневный автоматический запуск сбора по CRON-расписанию. |
| FR-11 | MUST | Учёт статистики ведётся по дате **публикации** `published_at`, а не по дате парсинга. |
| FR-12 | MUST | Каждый прогон фиксируется в журнале (`ingestion_runs`): время старта/финиша, статус, кол-во новых/обновлённых/ошибок. |
| FR-13 | SHOULD | Возможность ручного запуска прогона (admin-эндпоинт / CLI-команда) для отладки и бэкфилла. |
| FR-14 | SHOULD | Поддержка исторического бэкфилла за прошлые даты публикации в пределах доступного на hh.ru. |

### 1.2a. Массовый backfill (Phase 8 — реализовано)

> Уточняет и реализует FR-13/FR-14. Единоразовый полный сбор активного пула Frontend-вакансий; далее ежедневный CRON (§1.2) инкрементально докидывает новые.

| ID | Приоритет | Требование | Статус |
|----|-----------|------------|--------|
| FR-48 | Phase 8 | **Массовое первичное наполнение (backfill):** CLI-команда `python -m app.cli backfill --days-back N` загружает ВСЕ доступные по поиску hh.ru активные Frontend-вакансии за заданное количество дней назад. Источник — HTML (primary, `HtmlVacancySource`); API — опциональный путь за флагом `HH_API_FALLBACK_ENABLED`. | ✅ Реализовано |
| FR-49 | Phase 8 | **Полнота сбора — обход лимита ~2000 результатов hh.ru:** probe-запрос получает счётчик найденных (`found`) из HTML; при `found >= ~1900` и окне > 1 дня — интервал рекурсивно делится пополам по датам, каждая половина обрабатывается отдельно. Минимальная гранулярность сегмента — 1 день (ниже дня hh.ru не фильтрует). Формат фильтра дат HTML-поиска — **только `DD.MM.YYYY`**. | ✅ Реализовано |
| FR-50 | Phase 8 | **Глобальный дедуп между сегментами:** идентификаторы `hh_vacancy_id`, собранные в разных сегментах, дедуплицируются на уровне прогона (set); повторные вакансии обрабатываются upsert (FR-4). | ✅ Реализовано |
| FR-51 | Phase 8 | **Resumability:** батч-коммиты по 50 вакансий — промежуточные данные сохраняются в БД; при сбое/капче уже обработанное не теряется. Прогон фиксируется в `ingestion_runs` (`meta.type = backfill`, `meta.source`, счётчики `created`/`updated`/`filtered`/`errors`/`captcha_blocks`). | ✅ Реализовано |

> Уточняет основной путь сбора (FR-2). На момент проектирования Phase 2 `api.hh.ru` недоступен, поэтому HTML-парсинг — primary.

| ID | Приоритет | Требование |
|----|-----------|------------|

| FR-39 | MUST | Обнаружение **капчи/блокировок/anti-bot**: при срабатывании прогон помечается, применяется backoff/пауза; средства защиты **не обходятся** (соблюдение ToS). |

### 1.8. Фильтрация релевантности (Relevance Filtering)

> Поиск hh.ru по запросу «frontend junior/middle/senior» возвращает много нерелевантных вакансий (Fullstack, Backend, руководитель проектов, QA и т.п.). Они не должны попадать в БД как валидные Frontend-вакансии.

| ID | Приоритет | Требование |
|----|-----------|------------|
| FR-41 | MUST | В пайплайне нормализации между извлечением (**parse**) и записью (**upsert**) выполняется отдельный шаг **Relevance Filtering** — классификация вакансии «релевантно / мусор». Нерелевантные вакансии **не сохраняются** как валидные. |
| FR-42 | MUST | Классификация для MVP — **rule-based** (без LLM): по словарю **положительных маркеров** Frontend (frontend, фронтенд, react, vue, angular, javascript, typescript, верстка, html, css и т.п.) и словарю **стоп-сигналов** (fullstack, фуллстек, backend, бэкенд без явного frontend-уклона, руководитель проекта/проектов, project manager, QA, DevOps, аналитик, дизайнер и т.п.). |
| FR-43 | MUST | Логика разрешения конфликтов (есть и frontend-, и стоп-маркеры) описана и конфигурируема: **приоритет заголовка над описанием**, скоринг сигналов и **конфигурируемый порог** принятия; политика по умолчанию задокументирована (см. [`02-architecture.md`](02-architecture.md) §2.3a). |
| FR-44 | MUST | Словари ключевых/стоп-слов и порог **конфигурируемы** (конфиг-файл и/или таблицы БД), а не захардкожены, чтобы заказчик мог корректировать их без изменения кода. |
| FR-45 | SHOULD | Число и доля **отфильтрованных** (отброшенных) вакансий за прогон **считаются и логируются** как метрика (расширение `ingestion_runs`). |
| FR-46 | COULD | Опциональная таблица/лог **аудита** отфильтрованных вакансий (`hh_vacancy_id`, заголовок, причина/сработавшее стоп-слово) для последующей настройки словарей. Не является валидными данными для метрик. |
| FR-47 | MUST | **Грейд** (Junior/Middle/Senior) определяется **отдельным шагом** уже **после** прохождения фильтра релевантности (см. FR-6). |

## 2. Нефункциональные требования (Non-Functional Requirements)

### 2.1. Производительность (Performance)

| ID | Приоритет | Требование |
|----|-----------|------------|
| NFR-1 | MUST | Ответ API по дашбордным метрикам — **p95 < 500 мс** при чтении предрассчитанных snapshots. |
| NFR-2 | MUST | Дашборды используют предрасчитанные агрегации, а не «тяжёлые» запросы на лету. |
| NFR-3 | SHOULD | Полный ежедневный прогон сбора Frontend-вакансий по РФ укладывается в окно обслуживания (ориентир — десятки минут) с учётом rate-limiting. |

### 2.2. Надёжность и доступность (Reliability)

| ID | Приоритет | Требование |
|----|-----------|------------|
| NFR-4 | MUST | Сбой одной вакансии/страницы не прерывает прогон (graceful degradation). |
| NFR-5 | MUST | Retry с экспоненциальной задержкой и jitter для сетевых ошибок и `429/5xx`. |
| NFR-6 | MUST | Идемпотентность прогонов: повторный/частично завершённый прогон не портит данные. |
| NFR-7 | SHOULD | Защита от частичных агрегаций: пересчёт метрик в транзакции / атомарная замена snapshot. |

### 2.3. Юридические и этические аспекты парсинга + rate-limiting

| ID | Приоритет | Требование |
|----|-----------|------------|
| NFR-8 | MUST | **Вежливый краулинг HTML** (основной путь): уважение `robots.txt` и ToS hh.ru; **без обхода капч и средств защиты**. При доступности официального `api.hh.ru` (fallback) — соблюдение его условий использования и лимитов. |
| NFR-9 | MUST | **Rate-limiting исходящих запросов**: ограничение RPS, **задержки между запросами** (в т.ч. рандомизированные), уважение заголовков `Retry-After` и кодов `429`. |
| NFR-10 | MUST | Корректный идентифицирующий `User-Agent` с контактом (как при HTML-краулинге, так и при обращении к api.hh.ru). |
| NFR-11 | MUST | **Устойчивость HTML-парсинга к изменению вёрстки**: селекторы вынесены в конфиг (FR-37); при массовом провале извлечения полей прогон помечается и не затирает корректные данные. |
| NFR-12 | SHOULD | Хранение только агрегатов и обезличенных атрибутов вакансий; не хранить персональные данные сверх необходимого. |
| NFR-13 | SHOULD | Параметры лимитов (RPS, задержки, размер батча), селекторы парсинга и словари релевантности — конфигурируемы (env / конфиг / таблицы БД). |
| NFR-31 | MUST | Ретраи сетевых/парсинговых ошибок через **tenacity** (экспоненциальный backoff + jitter) согласованы с rate-limiting; временная блокировка/капча трактуется как сигнал к паузе, а не к агрессивным ретраям. |
| NFR-33 | Phase 8 | **Вежливый краулинг при объёмном историческом обходе (backfill):** массовый backfill (сотни-тысячи запросов) соблюдает rate-limiting (aiolimiter), рандомизированные задержки и ретраи (tenacity) на том же уровне, что и ежедневный CRON-сбор; при обнаружении капчи — пауза, не обход. |
| NFR-34 | Phase 8 | **Устойчивость/resumability массового прогона:** частичный сбой (сетевая ошибка, капча, таймаут) не теряет уже сохранённые данные; батч-коммиты гарантируют инкрементальное сохранение; прогон можно перезапустить (idempotent upsert). |

Для доверия к цепочке вводится настройка `LLM_CA_BUNDLE` (путь к PEM); при заданном значении используется кастомный httpx-клиент с этим CA, **верификация TLS не отключается**. Сертификат хранится в `backend/certs/x5_root_ca.pem` (в `.gitignore`; в проде — через секреты K8s). |

# 01 — Требования (Requirements)

> Нумерация: **FR-x** — функциональные требования, **NFR-x** — нефункциональные.
> Приоритеты: **MUST** (обязательно для MVP), **SHOULD** (желательно), **COULD** (опционально), **LATER** (поздние фазы 6–7).

---

## 1. Функциональные требования (Functional Requirements)

### 1.1. Сбор данных (парсинг)

| ID | Приоритет | Требование |
|----|-----------|------------|
| FR-1 | MUST | Система собирает вакансии с hh.ru по специальности **Frontend**, регион — **вся Россия**. |
| FR-2 | MUST | Основной путь сбора — публичный API `api.hh.ru` (эндпоинт `GET /vacancies` с фильтрами + `GET /vacancies/{id}` для деталей). |
| FR-3 | MUST | При недоступности/изменении API — **фолбэк на HTML-скрейпинг** страниц hh.ru. Переключение логируется. |
| FR-4 | MUST | Сбор **идемпотентен**: повторный парсинг той же вакансии не создаёт дубликат, а обновляет запись (upsert по `hh_vacancy_id`). |
| FR-5 | MUST | Для каждой вакансии сохраняются: `hh_vacancy_id`, название, работодатель, зарплата (от/до, валюта, gross/net), `published_at`, опыт, формат работы, ключевые навыки, грейд, ссылка на оригинал. |
| FR-6 | MUST | Грейд (Junior/Middle/Senior) определяется по полю опыта hh.ru и эвристикам по названию/описанию (см. [`04-metrics.md`](04-metrics.md) §«Определение грейда»). |
| FR-7 | MUST | Нормализация данных: валюты, единый справочник навыков (skill canonicalization), формат работы, опыт. |
| FR-8 | SHOULD | Система фиксирует «сырой» ответ источника (`raw_payload` JSONB) для возможности переобработки без повторного парсинга. |
| FR-9 | MUST | Сбор устойчив к частичным сбоям: ошибка по одной вакансии не прерывает весь прогон; ведётся учёт успешных/неуспешных. |

### 1.2. Планировщик (scheduler / CRON)

| ID | Приоритет | Требование |
|----|-----------|------------|
| FR-10 | MUST | Ежедневный автоматический запуск сбора по CRON-расписанию. |
| FR-11 | MUST | Учёт статистики ведётся по дате **публикации** `published_at`, а не по дате парсинга. |
| FR-12 | MUST | Каждый прогон фиксируется в журнале (`ingestion_runs`): время старта/финиша, статус, кол-во новых/обновлённых/ошибок. |
| FR-13 | SHOULD | Возможность ручного запуска прогона (admin-эндпоинт / CLI-команда) для отладки и бэкфилла. |
| FR-14 | SHOULD | Поддержка исторического бэкфилла за прошлые даты публикации в пределах доступного на hh.ru. |

### 1.3. Агрегации и метрики

| ID | Приоритет | Требование |
|----|-----------|------------|
| FR-15 | MUST | Расчёт зарплатных метрик: медиана, минимум, максимум, перцентили (p10, p25, p75, p90). |
| FR-16 | MUST | Мультивалютность: приведение RUB/USD/EUR к базовой валюте (RUB) по курсу на дату публикации. |
| FR-17 | MUST | Учёт gross/net: приведение к единому виду (по умолчанию net) с настраиваемым коэффициентом НДФЛ. |
| FR-18 | MUST | Корректная обработка «вилок» (от/до), односторонних вилок и вакансий **без зарплаты** (исключаются из зарплатных метрик, но учитываются в counts). |
| FR-19 | MUST | Рейтинг навыков по грейдам (топ-N навыков для Junior/Middle/Senior с частотой и долей). |
| FR-20 | MUST | Анализ работодателей: топ компаний по числу публикаций за период. |
| FR-21 | MUST | Динамика во времени с фильтрами: день / неделя / месяц / год. |
| FR-22 | SHOULD | Дополнительные метрики: распределение по грейдам, по формату работы (офис/гибрид/удалёнка), по опыту, рост/падение спроса (тренд), топ-связки навыков (co-occurrence). |
| FR-23 | SHOULD | Предрасчёт агрегаций (snapshots) для быстрых дашбордов; пересчёт после каждого прогона. |

### 1.4. API (backend)

| ID | Приоритет | Требование |
|----|-----------|------------|
| FR-24 | MUST | REST API отдаёт метрики с фильтрами по периоду, грейду, валюте, gross/net (см. [`06-api-contract.md`](06-api-contract.md)). |
| FR-25 | MUST | Эндпоинт здоровья (`/health`) и статуса последнего прогона сбора. |
| FR-26 | SHOULD | Пагинация и сортировка для списочных эндпоинтов (вакансии, работодатели, навыки). |
| FR-27 | SHOULD | Версионирование API (`/api/v1/...`). |

### 1.5. Frontend (дашборды)

| ID | Приоритет | Требование |
|----|-----------|------------|
| FR-28 | MUST | Дашборд с ключевыми зарплатными метриками и графиками по грейдам. |
| FR-29 | MUST | Визуализация рейтинга навыков, топа работодателей, динамики во времени. |
| FR-30 | MUST | Глобальные фильтры: период (день/неделя/месяц/год), грейд, валюта, gross/net. |
| FR-31 | SHOULD | Минимальное хранение данных на фронте (кэш запросов через TanStack Query), без собственной БД. |
| FR-32 | COULD | Экспорт графика/данных (PNG/CSV). |

### 1.6. LLM-фичи (поздние фазы)

| ID | Приоритет | Требование |
|----|-----------|------------|
| FR-33 | LATER (Phase 6) | LLM-анализ рынка по специальности: текстовые инсайты/резюме трендов на основе агрегированных данных. |
| FR-34 | LATER (Phase 6) | Доступ к LLM через **абстрактный adapter** (провайдер заменяем); реализация по X5 CoPilot API. |
| FR-35 | LATER (Phase 7) | Загрузка резюме пользователем (файл/текст) и оценка «профпригодности»: соответствие рынку, прохождение фильтров по ключевым словам, рекомендации. |
| FR-36 | LATER (Phase 7) | Сопоставление навыков резюме с востребованными навыками рынка (в т.ч. через embeddings). |

## 2. Нефункциональные требования (Non-Functional Requirements)

### 2.1. Производительность (Performance)

| ID | Приоритет | Требование |
|----|-----------|------------|
| NFR-1 | MUST | Ответ API по дашбордным метрикам — **p95 < 500 мс** при чтении предрассчитанных snapshots. |
| NFR-2 | MUST | Дашборды используют предрасчитанные агрегации, а не «тяжёлые» запросы на лету. |
| NFR-3 | SHOULD | Полный ежедневный прогон сбора Frontend-вакансий по РФ укладывается в окно обслуживания (ориентир — десятки минут) с учётом rate-limiting. |

### 2.2. Надёжность и доступность (Reliability)

| ID | Приоритет | Требование |
|----|-----------|------------|
| NFR-4 | MUST | Сбой одной вакансии/страницы не прерывает прогон (graceful degradation). |
| NFR-5 | MUST | Retry с экспоненциальной задержкой и jitter для сетевых ошибок и `429/5xx`. |
| NFR-6 | MUST | Идемпотентность прогонов: повторный/частично завершённый прогон не портит данные. |
| NFR-7 | SHOULD | Защита от частичных агрегаций: пересчёт метрик в транзакции / атомарная замена snapshot. |

### 2.3. Юридические и этические аспекты парсинга + rate-limiting

| ID | Приоритет | Требование |
|----|-----------|------------|
| NFR-8 | MUST | Приоритет официального `api.hh.ru`; соблюдение его условий использования и лимитов. |
| NFR-9 | MUST | **Rate-limiting исходящих запросов**: ограничение RPS, пауза между запросами, уважение заголовков `Retry-After` и кодов `429`. |
| NFR-10 | MUST | Корректный идентифицирующий `User-Agent` с контактом (по требованиям hh.ru API). |
| NFR-11 | MUST | HTML-скрейпинг — только фолбэк; уважение `robots.txt` и ToS; без обхода капч и средств защиты. |
| NFR-12 | SHOULD | Хранение только агрегатов и обезличенных атрибутов вакансий; не хранить персональные данные сверх необходимого. |
| NFR-13 | SHOULD | Параметры лимитов (RPS, задержки, размер батча) — конфигурируемы через env. |

### 2.4. Приватность (особенно данные резюме, Phase 7)

| ID | Приоритет | Требование |
|----|-----------|------------|
| NFR-14 | LATER (Phase 7) | Резюме пользователя обрабатывается **минимально необходимо**; по умолчанию **не хранится** на сервере (in-memory / эфемерно). |
| NFR-15 | LATER (Phase 7) | Явное согласие пользователя на обработку и (опционально) на временное хранение; прозрачная политика удаления. |
| NFR-16 | LATER (Phase 7) | Передача резюме в LLM-провайдер сопровождается предупреждением; по возможности — обезличивание PII (имя, телефон, e-mail) перед отправкой. |
| NFR-17 | LATER (Phase 6–7) | `API_KEY` и секреты — только в `.env` / секрет-менеджере, **никогда** в репозитории, логах и ответах API. |

### 2.5. Наблюдаемость и логирование (Observability)

| ID | Приоритет | Требование |
|----|-----------|------------|
| NFR-18 | MUST | Структурированное логирование (JSON) с уровнями; correlation-id на прогон сбора и на HTTP-запрос. |
| NFR-19 | MUST | Метрики прогона сбора: число новых/обновлённых/ошибочных вакансий, длительность, доля фолбэков на HTML. |
| NFR-20 | SHOULD | Health-/readiness-проба и эндпоинт статуса последнего прогона. |
| NFR-21 | COULD | Экспорт метрик в Prometheus-формате; дашборд эксплуатации. |

### 2.6. Безопасность (Security)

| ID | Приоритет | Требование |
|----|-----------|------------|
| NFR-22 | MUST | Все секреты — через переменные окружения; `.env` в `.gitignore`. |
| NFR-23 | SHOULD | CORS настроен явно для домена фронтенда. |
| NFR-24 | SHOULD | Валидация и санитизация всех входных параметров API (Pydantic). |
| NFR-25 | COULD | Rate-limiting на входящие запросы публичного API. |

### 2.7. Сопровождаемость и переносимость (Maintainability / Portability)

| ID | Приоритет | Требование |
|----|-----------|------------|
| NFR-26 | MUST | Запуск всего стека через **Docker Compose** (api, db, frontend, scheduler). |
| NFR-27 | MUST | Миграции схемы БД через **Alembic** (версионируемые, обратимые). |
| NFR-28 | MUST | Слой LLM изолирован за интерфейсом-адаптером (замена провайдера без изменения бизнес-логики). |
| NFR-29 | SHOULD | Покрытие критичной логики (нормализация, метрики, dedup) автотестами. |
| NFR-30 | SHOULD | Линтинг/форматирование (ruff/black для Python, ESLint/Prettier для фронта). |

## 3. Допущения и ограничения (Assumptions & Constraints)

- **A1.** Состав и формат публичных ручек `api.hh.ru` могут меняться — отсюда обязательный HTML-фолбэк (FR-3) и хранение `raw_payload` (FR-8).
- **A2.** Курсы валют берутся из внешнего источника (ЦБ РФ) и кэшируются по датам; при недоступности — последний известный курс. Детали — в [`04-metrics.md`](04-metrics.md).
- **A3.** Детали интеграции с LLM (X5 CoPilot API) частично уточняются на Phase 6 из [`CopilotAPI.pdf`](../CopilotAPI.pdf); базовые параметры уже зафиксированы в [`05-tech-stack.md`](05-tech-stack.md).
- **A4.** MVP без пользовательской аутентификации; публичные дашборды.
